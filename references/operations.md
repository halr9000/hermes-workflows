# Run operations and read model

Use `workflow{action:"run", graph:<object>}` (or `from:<saved-name>`, or `graph_path:<absolute-local-JSON-file>`), then `status` and `wait` with the returned `run_id`. The runner outlives your turn: terminal transitions wake the owner session (`wake.jsonl` is the ledger); after a host restart or a swallowed wake, sweep your open runs once with `status`/`list`, then `wait` them to a boundary or revive an `interrupted`. For a reusable graph, `save` first and `run from:<name>` next; `library` lists it richly (name, description, tags, provenance, path-relative id). Discovery is a CONTINUOUS admission gate (est-2ek.1.828, owner ruling 16): every shelf graph is structural-validated at every listing (defaults fill + the door validator, after envelope normalization, no route/model ping) — an entry that fails is omitted as a typed `skipped`/`quarantined` row and never replays from discovery; passing entries and bare legacy bytes are byte-identical rows. Optional study-only `submit` takes `why_not_library` (>=80 chars) and quarantines the submission under `runs_root()/inbox`, never the library; `inbox` lists submissions newest-first for a human-gated promotion review. Ordinary one-off `run` executes without lookup, tags, save or submission. `graph_path` is for an unsaved caller-authorized local file on run/save/amend, not a remote path. `/wf` is an optional library front end.

A run may be running, held, interrupted, done, failed or stopped. Running requires a live process with the exact runner command and run identity; a persisted PID or parked marker is not sufficient. Held gates and interrupted runs do not count as running. List responses include full-census `counts` and `total` even when the recent-runs page is truncated. `interrupted` means unfinished work with no live runner: inspect saved outputs and uncertain side effects before explicitly resuming with `wait`. A recorded fatal runner crash is `failed` and needs correction/amend rather than repeated wait/respawn. Every `status`/`wait` payload carries the derived `next` — do what it says and `wait` again until it is empty; alongside it rides the derived `failed_nodes` (`[{id, error, error_class}]`) — WHICH nodes died, derived from the same efp-valid committed states the status verdict used, never stored; a crash verdict with no failed node reads `[]` (honest absence: the runner died, not a node) (`wait` self-yields with a "call wait again" note before a terminal state to stay inside the host deadline). On a held gate `next` names the gate and its options: ask the owner, then `release` with the exact answer. A machine gate may park without a child; read its check attempt, last exit/tail and deadline.

`status.nodes` uses committed results for scheduling and projects an uncommitted child spawn as running only when its recorded process identity is still verified. `blocked_by` points to unfinished ancestors. Child spend metrics are cumulative across attempts/graph amendments. Liveness and heartbeat come only from exact, currently verified child process/session identities: `active_spawns` lists all active fan-out children, while `active_spawn` retains the first for existing consumers. Node and per-item metrics do not count old unended database rows as live; missing current activity means unknown idle, not zero. Not every run has a metrics row. Missing API-call evidence is unknown, never zero; retry after uncertain effects may duplicate them. Failed and partial nodes ship `node_facts` (`error_class`, `attempts`, `attempts_log`, the child's `final` words, `log_path`, `prompt_path`) beside the error line. A turn-cap death (`cap_exhausted`) is typed only when the child's core quiet-turn report carries the loop's own budget stamp (`max_iterations_reached(n/m)`); prose about turn limits is never trusted, and an untyped budget death stays `unknown`. The runner is process-tree aware (#61): an exit-0 spawn is judged only when its /proc tree is empty — progress chatter over a live tree is `left_live_descendants` (a verdict comes from the run's exit code after its tree is empty, never from prose), a fenced answer over a live tree commits `partial` with `tree_proof: dead` + `tree_descendants` (the solo `node.finished` event carries the class too when a tree had to be accounted for), and every retry proves the prior attempt's tree dead before re-spawning or fails closed. The walk is recursive and the tracked pid-set persists across the retry ladder: double-fork/setsid descendants that reparent are still found and re-adopted, never under-counted. Registry rows (the survivor registration a detached descendant may pin) are CLAIMS, never permissions: a row authorizes a signal only while /proc still vouches for its occupant (kernel start-tick equality at registration time), legacy rows are inert, and a boot sweep that ends stuck/unknown blocks admission before any child spawns (#80: after PID reuse, an unverified row is a loaded gun at a stranger; an alive predecessor tree is never scheduled over). An unreadable /proc is unsafe, never empty (fail-closed, same family as the submit-time alive-proof gates); a machine without procfs keeps the honest-empty degradation. An adopted orphan whose tree outlives it never commits a clean `done` — the completeness error rides with the answer. Those `tree_*` keys appear only when a tree actually had to be accounted for. Stale runner exits do not suppress amended work. A pruned/skipped node is terminal, not done output.. A child that dies rc!=0 within ~1 s of spawn on a provider/alias config marker (`Unknown provider '<alias>' …`) is typed `config_input`: a deterministic input error, failed on the FIRST attempt with the respawn budget untouched — fix the node's provider pin or the seat config; a re-run of the same graph dies identically. A child that exits rc=130 carrying the CLI's own lease notice (`Stopped waiting for another Hermes process on this session. Your message was not processed.`) is typed `lease_busy`: another Hermes process held the session lease and the message never reached the model — a transient collision, so the node gets ONE bounded re-drive as a FRESH session under the next attempt key (never a resume of the busy session), preceded by `node.retrying error_class=lease_busy`. A rc=130 death without that notice keeps the ordinary classification.

`run.blocked` retains `failed` (failed node ids) and `blocked` (pending node ids gated by dependencies), and adds `unconverged` (done/partial ids whose descendant closure reaches a blocked-pending node) plus `blocked_by` (map from each blocked-pending id to the failed ancestor ids that gate it, including transitive ancestors). Lists preserve graph order. It also carries `residue` — `data_dead` (blocked ids reachable from a failed node over data edges only: they need the dead work redone), `order_dead` (blocked only through an `order_only` convoy edge: their own work never depended on the death) and `verdicts` (per `unconverged` id, `{status, verdict}` where `verdict` is the committed output's `verdict` string or null — read the verdict, never `status` alone: a `done` merge seat whose verdict is `not-approved` merged nothing) — and `dead_letter`: per failed id `{error_class, attempts, final_empty, attempts_log, last}`, where every `attempts_log` entry and `last` carry that attempt's own `tool_calls`/`api_calls` from state.db (absent when no row exists — never zeros), so an empty final capture is never classified alone. This is event legibility only; `WORKFLOW_FAILED` and the retry/respawn policy are unchanged. There is no runner dead-letter verb. A released-past-a-dead-convoy-member node logs `node.spliced` `{node, past:[dead ids]}` once before it runs.

`steer` queues text for a future child spawn; it does not inject into a running child or reopen a terminal run. To change a graph, submit the entire replacement via `amend` — or send `patch:{"nodes":{"<existing id>":{"<field>":value}}}` (shallow per-node field merge, null deletes; `name` optional top-level) so a two-field fix never resubmits the multi-KB graph: unknown ids, id changes, new nodes and any other patch key are refused by name, patch is exclusive with graph/graph_path, and the patched result goes through the FULL amend door (validation, CAS, frozen replay; amends.jsonl still records the resolved full graph). `dry_run:true` (or the `diff` action — the same door with dry_run FORCED) previews added/removed ids plus changed/will_rerun/unchanged plus `will_reset_running` — every node RUNNING at submit time; an amend resets those nodes and their live children re-run from zero regardless of whether their def moved, so read that list before amending a run with work in flight — and a unified `graph_diff`, without replacing the graph or spawning a runner. To check a graph before launching it, submit `run` with `dry_run:true`: the same pre-launch gates (including route pings, quota and live-route enforcement) return `{ok, dry_run, models, routes}` without a run dir, lane entry or runner spawn. Use `validate` for a static preview with no liveness ping. Added nodes and their downstream work appear in `will_rerun`; matching committed results replay-skip. Stop is not rollback; reconcile external effects before rerunning.

Silent death is loud by law (#8 item 2): when a `wait`/`release`/`amend`/`stop` respawns a runner whose predecessor died without recording a verdict (dead `wf.pid`, absent `runner_exit.json` — a stale fingerprint over a recorded exit is NOT a silent death), the tool appends `runner.reaped` (prev_pid + observed reason, once per death) and one `node.interrupted` (`{node, index, pid, skey, attempt, of_runner}` — the runner's item vocabulary) per node record still claiming a live child whose own record fails the spawn-verification law, to `events.jsonl` BEFORE spawning the replacement. A verifiably-live child (per fan-out item index included) is adopted, never interrupted; `status`/`wait` reads never write; falsely-claimed node records are left byte-intact (the events are the record). Watchers can therefore `tail events.jsonl` for `runner.reaped` instead of inferring death from absence.

Owner-session wake visibility has a deliberate boundary (#8 crash-visibility leg): the runner pushes each lifecycle transition — `gate.held`, `run.done`, `run.failed`, including a CATCHABLE crash caught by either exception net — to the owner session stamped in run.json, as finite runner-authored protocol text carrying inert run-id/event fields (graph, validator, child and exception prose stays attributed data). The `run.failed`/`run.done` payloads additionally carry runner-computed pointer fields (#501): `run_dir` (the run directory) and, on `run.failed`, `failed_node_logs` (the efp-valid committed failed-node records' `log_path` set) — omitted when unresolvable, never fabricated, so a woken session reads the failure it was woken for without archaeology. Wakes report facts only, never new repair, dispatch, PR or curation authority. A lifecycle event outside the emitted-event registry never goes unnoticed (est-jbcrw class-coverage law): it wakes on the fixed catch-all body and prints `WORKFLOW_WAKE_UNMAPPED_EVENT` on the runner's stdout — a class gap is a loud drift alarm, never silence. Delivery is best-effort and requires a reachable configured endpoint; it is not a substitute for blocking `wait` when push is unavailable. Two typed exceptions suppress the PUSH, never the record (WF-GRAFT-1): a `run.done` whose DECLARED verdict output (top-level `result:`, efp-valid) carries the Hermes `[SILENT]` marker, and a node-subject notice (`gate.held`, `fanout.stragglers`) under a `wake_tier` that quiets it. A suppression POSTs nothing, prints `WORKFLOW_WAKE_SUPPRESSED <run> <event> <reason>` on stdout, and writes exactly ONE probe row typed `suppressed` with `delivered:false` — re-driving the same transition instance adds no row and no POST, so a suppression is recorded once and never retried, and it is never a hole: the ladder, the table, and the fail-open rules are in [grammar.md](grammar.md#wake-noise-tiers-and-the-silent-verdict-optional). `run.failed` / `run.partial` are never suppressed, no tier governs a run-terminal wake, and the operator outbound mirror is untouched by either reason. `wait` can resume interrupted work; `status` is read-only. A CATCHABLE exception can attempt a wake; an uncatchable one cannot: SIGKILL (OOM, a cgroup sweep, `kill -9`) runs no Python at all, so no in-process net can record or push it — the run reads `interrupted`/`held` with no wake, and observation of a killed runner stays external supervision's job (the surviving-enclosing-service leg of #8, unclaimed here). The wake probe `<run>/wake.jsonl` records every attempt (delivered-or-recorded law). Retries of one transition reuse a stable Idempotency-Key; the pinned-core probe measures the core collapsing an in-window retry to one started/completed owner turn. This does not claim dedupe after cache eviction, core restart, or outside that measured window.

Mixed-version door/runner skew (#152): the door that answers a gate respawns the runner from ITS OWN bundled `wf.py`, so a release from an older install can consume a gate answer into an admission death the old runner inflicts on a newer committed graph (`crashed: graph invalid`) — the answer is then unrecoverable (`gate already answered`) and the lap must be re-walked. Two fail-closed laws keep the answer durable: the door runs the respawner's own admission validator over the committed `graph.json` BEFORE writing `gates/<id>.json` and refuses (`this door cannot drive this graph — drive it from its own tree (<offending node/field>)`, zero writes, hold intact); and a runner that still dies at admission graph-invalid un-consumes any answer whose gate node never committed done/skipped — `gates/<id>.json` -> `gates/<id>.json.unconsumed` (evidence, never deleted), event `gate.answer_unconsumed` carrying the prior answer's `at`, the exit record reads `interrupted: admission graph invalid` so the run stays resumeable and the next release from a capable door re-lands the answer. An answer already committed at a real boundary (node done/skipped) never un-consumes.

## Small, parent-gated escalation recipe (no new engine feature)

Use a terminal, decision-only agent node with no automatically runnable work descendants. Its ordinary schema-defined final JSON can contain `needs_escalation: true` and a short reason (the node schema must actually permit these fields). The parent inspects that exact value and any external effects, selects an explicit model and amends the graph with original committed inputs plus a bounded factual handoff. Check `dry_run`'s `will_rerun` before applying. A timeout remains a failed node, not a safe auto-retry: the parent investigates and decides. Never use this on a work-product node with downstream execution; schema-valid JSON is committed as done even if its text requests escalation. This recipe adds no tool, status, automatic fallback or guarantee of side-effect rollback.

Desktop cards use `::workflow{id="<run_id>"}` and are optional presentation. Plain CLI text and run IDs suffice. The existing desktop card hook may append cards; agents need not paste them. Backend and desktop installations are separate.

**Card ledger.** Owed cards are tracked in `<runs_root>/card-ledger.json` (`{session_id: {run_id: {state: pending|held, ts, name}}}`, atomic writes, a corrupt file reads as empty), kept by hooks rather than a run-dir scan: `post_tool_call` adds a run on every `workflow` launch, marks `held` gate reports, and drops it on `done|failed|stopped`/`stop`; `pre_llm_call` reminds the model of owed cards only while the ledger holds some; `transform_llm_output` appends up to 3 cards (newest first) and drops each entry once the text is selected. The old age-window setting (`card_window_minutes`) is gone, replaced by the ledger; entries surviving a gateway restart ship late. Every hook is fail-open.

`profile` routes an agent node to a named target profile, not a fan-out item: the child gets the TARGET's SOUL, memory, `.env` and tools. This is delegation, not isolation. Before launching, the target owner writes `<target_profile_home>/workflow_team.json` as `{"accept_from":["<launcher-profile-name>"]}`; the launcher name comes from the launching process's own HERMES_HOME (for the default profile, use `"default"`), never from a graph argument. The target must have `config.yaml`; `default` may launch but is never a target. Without target-owned consent validation fails before any run write/spawn; a target deleted before Popen fails with `error_class:"spawn"`, never silently falling back to the launcher.

## Execution clocks (read-only)

`status`/`wait` and the shared read model expose `nodes[id].clocks`:
- `phase` distinguishes `queued`, verified `active`, `held`, and typed `expired`
  from ordinary node states. It never changes scheduling or admission.
- `queue[]` reports item index, elapsed time since the existing `seat.wait` event,
  configured timeout and `remaining_upper_bound_s`. The event follows admission-clock
  start, so this is an upper bound, not an exact deadline or dispatch ETA.
  A `seat_wait` death reports `exhaustion_reason: queue_timeout`; its `ms` is queue
  duration, not child work. Fingerprint-valid literal fan-out item records also
  supply grouped `item_expirations` reason counts and observed queue-seconds
  (unknown duration counts when needed), without relabeling a mixed node as
  expired. Stale items are excluded; dynamic inventory remains unknown.
  The existing runner gives queue and spawn separate walls.
- `active[]` starts only from verified spawns. `configured_remaining_s` subtracts
  elapsed time from the baked timeout, not from an invented task-total budget.
  `effective_remaining_s` is null: credential parks and extensions can alter the
  enforced attempt deadline, which the existing records do not fully expose.
- `work` sums observed child/child_end ledger intervals across attempts. Open
  intervals count through now only for verified live children; others increment
  `unknown_intervals`; orphan ends and verified active children without starts
  also count as known gaps. An unavailable/partial ledger with no countable gaps
  reports null, not zero. Counts describe known gaps, never prove completeness.
  Node and run accounting explicitly retain `coverage: best_effort`,
  `completeness: unknown` and `lower_bound: true`. These are child-seconds,
  not elapsed wall time; missing evidence cannot prove zero actual work.
  Each read indexes a single prefix of at most 4 MiB, with `accounting.ledger`
  reporting bytes, budget and read/partial/unavailable status. Partial lines are
  excluded. Ordinary list/census projections skip telemetry they do not return.
- `hold` uses the fingerprint-valid held marker. Missing starts remain unknown.
  No `hold_timeout` means `unbounded`. An expired timeout without `default_option`
  **keeps holding**; expiration is not cancellation, release or an answer.

Run `accounting` sums observed child-seconds across the current graph's nodes,
items and attempts. Work from removed nodes is outside this current-node fold.
`task_total_ceiling: not_enforced` states the existing policy: retries, repairs,
checks and resumed runs do not share an enforced task-total authorization cap.
Adding one or bounding indefinite holds requires a separate owner decision; this
visibility change neither grants budget nor claims the stronger P02 proposal is met.
`item_counts` uses literal fan-out item count, with done/partial/failed/cancelled/
unknown distinct. Dynamic item totals currently remain unknown. A done record is
execution completion, never independent verification or an ETA.

## Lanes: in-flight dedupe for pollers

`run` accepts an optional `lane_key` (≤128 chars) and `status` accepts `lane_key` as an alternative to `run_id` (never spawning anything). The registry is an advisory index under a per-key kernel lock: while a claim is held, a second `run` with the same key never spawns — the UNFINISHED INCUMBENT WINS. Dedupe response: `{deduped:true, run_id, state, runner_live, needs_resume, last_event_ts, hint}` with the incumbent's ids, regardless of runner liveness — an interrupted incumbent is RESUMED (`wait run_id=<id>`), never replaced; resume stays with `wait`/supervisor under the existing per-run flock. `stop` on the incumbent is the explicit abandonment: terminal `stopped` releases the key and the next claim creates a fresh run. Keys are global per runs root — callers prefix `<team>/` themselves. Entries are append-only (never deleted); a stored key must equal the supplied key exactly (collision → error, never dedupe against a different key). `status lane_key=<key>` answers `{lane_key, run_id, state, runner_live, unfinished, needs_resume, last_event_ts}` (runner_live is /proc truth, not a persisted marker; `needs_resume` = unfinished AND runner dead — the poller's signal to `wait`); an unseen key returns `run_id:null, unfinished:false`. `list` rows carry `lane_key`/`team` when present. A `team` label (≤64) on `run` stamps run.json and shows in `list`; it changes nothing about scheduling. `list` also answers a per-root provenance rollup `provenance:{dispatched_by_set,total}` — a fold over the run.jsons the list loop already reads (zero extra scans): runs with a `dispatched_by` stamp count toward both counters, runs without it (or with a null stamp) count toward `total` only. The key is emitted ONLY when at least one run carries the stamp — a plain single-profile root keeps the original `{runs,total,counts}` key set. These field names are a published contract — consumers read `provenance.dispatched_by_set` / `provenance.total`; renaming them is a breaking change for consumers.

## Runs root, identity, and the trust boundary

Runs live under `<runs_root>` = `$WF_RUNS_ROOT` when set (absolute dir), else `<hermes_home>/workflows`, where `<hermes_home>` is the *resolved* profile home (core's `get_hermes_home()` when importable — so a profile-scoped tool call on a supervisor/multiplexed host uses the profile's home, not the launch-root `$HERMES_HOME` — else the raw `$HERMES_HOME`) — one resolver shared by the tool entry point, runner, dashboard, and liveness. Pointing `WF_RUNS_ROOT` at a shared directory lets runs created by a named profile survive deletion of that profile: `wait`, `status`, and the dashboard read them from anywhere. A run's `run.json` gains identity keys ONLY when derivable (a solo default-profile run with no `WF_RUNS_ROOT` adds nothing): `dispatched_by` (launcher profile name), `launch_root`, `team`, `lane_key`, `targets[]` (distinct node profiles), `graph_source` (when replaying a provenance-carrying library graph). Every child spawn carries the absolute run dir so its `inbox` pull resolves without guessing the root. TRUST BOUNDARY: a shared `WF_RUNS_ROOT` — or its owner-settings equivalent `plugins.entries.hermes-workflows.settings.runs_root`, which outranks it — is a COMMON-TRUST surface — same OS user, any profile that can reach the runs root may read, steer, and stop every run there. `dispatched_by`/`owner`/`source` stamps are provenance, not access control; nothing enforces them. Do not treat team fields as an ACL, and do not share a runs root across trust domains — the plugin has no isolation to offer there.

A run freezes its `hermes_bin` and plugin spawn cwd in `run.json` at launch: a tooling rotation or plugin-dir rename after launch kills unfinished runs at the next respawn — spawn-typed deaths on paths that no longer exist, not a defect in the definition you were debugging. Repair the frozen paths in `run.json` (`amend` never rewrites run meta), then re-drive, and census sibling runs before treating one death as isolated.

**Frozen-route flag strip (est-yq2xq).** Where a gateway's frozen-route resume policy refuses creation overrides under `--continue <skey> --create-if-missing` (every child dies rc=2 with "Resume retains gateway session policy; creation overrides are unsupported on resume", even on brand-new session keys), set `WF_OMIT_POLICY_FLAGS=1` in the runner's environment or create the marker file `<hermes_home>/workflows/omit-policy-flags.on` (the resolved home the runs root lives under). The spawn then omits every frozen-route creation-override pair — `--max-turns`, `--run-budget`, `--reasoning`, `-t`, `-m`, `--provider` — and children ride seat defaults: per-node model/provider pinning, reasoning, toolsets, turn caps and run budgets are UNAVAILABLE while on (a pinned lane silently runs the seat's default model). Marker absent and env unset = byte-identical stock argv; turn the feature off by deleting the marker and unsetting the env. This is a carried workaround, not a feature to keep: the structural fix is gateway-side (freeze the creation flags on the create-if-missing shape, est-yq2xq), and the switch is retired the day that lands.

Run directories carry no retention guarantee — a deployment janitor may purge sealed runs. Never point a live service, unit, route or checkpoint at a path inside a run dir; promote anything that goes live into a durable home the same turn it lands.

## Owner settings: `runs_root` and `profile` (tool-bridge first-class, #41/#42)

**Runs root precedence.** `plugins.entries.hermes-workflows.settings.runs_root` > `$WF_RUNS_ROOT` > `<hermes_home>/workflows` (resolved home) > `$HOME/.hermes/workflows`. The setting is read at CALL time through the same plugin-scoped helper `hermes_bin` uses (`PluginContext.get_config`; a process without a plugin ctx — runner, dashboard API, tests — reads the resolved home's `config.yaml` raw), so flipping it in `config.yaml` moves the tool entry point, `list`, `status`, liveness (`effective_runs_root`) and the dashboard together with no restart. The raw read mirrors core's loader semantics exactly (`wfcommon._expand_config_value` ports `hermes_cli/config.py` `_expand_env_vars`; `owner_setting` falls back to the legacy `config` subtree PER KEY, as `PluginContext.get_config` does): `${VAR}` / `${env:VAR}` templates expand identically on every reader, and a ref whose variable is unset stays verbatim in core — so every reader then REFUSES it with the same `unresolved ${...} reference` error instead of only the launching path seeing a value. Core's managed-scope overlay (`hermes_cli/config.py` `_merge_managed_overlay`) applies only to the ctx read and is NOT mirrored by the raw reader for these two keys — a deployment that overlays `runs_root`/`profile` via the managed scope must also write them to `config.yaml`, or every raw reader will answer the file's value. Validation is FAIL-CLOSED: `expanduser` is applied, the result must be absolute, it must not resolve to the Hermes `profiles/` root itself (run dirs, `lanes/`, and `library/` would be minted as sibling PROFILE directories, mixing every profile's namespace into one runs root), and it must not resolve inside another profile's home under the Hermes root (`<hermes_root>/profiles/<name>/`, the directory core's `-p` names live in) — a typo pinning the shared root to one profile's private dir would make every other profile's runs vanish into it; the caller's OWN profile home stays legal (it is the ordinary per-profile default). A malformed value is an `owner settings invalid: …` error on every action, never a silent fallback to another root. Unset = byte-identical to the precedence above without the first term.

**Identity sources, ranked.** `launcher_profile()` answers (1) the process's own resolved `HERMES_HOME` when it is `<root>/profiles/<name>` → `name`; else (2) `settings.profile` (validated by the same `_PROFILE_NAME_BAD` rule node `profile:` keys use; unsafe → error; and FAIL-CLOSED on a GHOST — the named profile home `<hermes_root>/profiles/<name>/` must EXIST, so a stamped `dispatched_by` nobody can verify is refused at submit with `does not exist` instead of inventing an identity that poisons the consent model; the check applies to the RESOLVED value whatever subtree it came from, settings or legacy `config`); else (3) `"default"`. Env-derived identity ALWAYS wins when present — the setting can only fill an identity the process could not carry (the desktop tool bridge and env-blind gateways launch the tool without a profile home), never override one it does. Consent gates (`workflow_team.json` `accept_from`) then see the real launcher instead of `default`, and `dispatched_by`/`provenance.owner` stamp it. Unset = byte-identical `"default"`.

**Spawn-ledger (the legibility half of #8; claim boundary stated honestly).**
`<run>/spawn-ledger.jsonl` is written by the ADMITTED RUNNER ONLY (sole-owner
law, same as `wf.pid`): one `role:runner` row at admission (right after
`ready_stamp`), one `role:child` row per recorded spawn, one `role:child_end`
row per judged spawn, every row carrying `{ts,pid,role,node,index,skey,purpose:
"workflow-runner"}`. It is the EXEMPTION HINT for EXTERNAL reapers — a process
sweep, a janitor cron, a human `pkill`: consult the ledger before killing, a
listed pid is a workflow runner or a workflow child and reapers must not kill
it. The boundary is honest: core's `process_registry` lives OUTSIDE this repo;
the plugin cannot change core, register anything there, or compel any reaper —
it can only make the tree legible (same honesty style as the claim boundary in
`tests/test_daemonize_8.py`). Best-effort by law: a ledger write failure never
touches a spawn.

**Invariant: a launch must never be invisible.** Whatever process launches a run — tool bridge, gateway, CLI, dashboard — the run lands under the ONE root every reader resolves, and every reader resolves it from the same ranked sources at the same call. There is no second root a tab can look at that the launching path does not write to. If the owner's setting is wrong, the launch says so and refuses; it does not quietly create runs somewhere else.

**Trust note.** `runs_root` and `profile` are OWNER vocabulary: they live in the owner's `config.yaml`, next to `hermes_bin` and `models`. They are deliberately NOT tool arguments — a model-settable graph/run arg could choose the launcher identity or the root, which is exactly the spoof the consent gate exists to refuse, and the hand-roll incentive (#41) dies with a setting the owner declares once, not with an argument the model could set per call. Nothing in the skill or the tool description tells the model to self-serve these keys; a model that edits `config.yaml` mid-session is acting on the owner's config, not on the tool's grammar, and env-derived identity still wins over anything it writes.

## Smart defaults (#50 audit)

A read-only pass over the tool's defaults — what a first-time agent would wish were different, and why each default stays as it is. Behavior is NOT changed here; an entry flagged `issue-worthy` is a candidate follow-up, nothing more.

- **`run` `lane_key` — default: unset (no lane).** A first-time user wishes dedupe were automatic (hash the graph, key on it) — pollers re-fire duplicates constantly and remembering to pass a key is a chore. Current is right: the registry keys are caller-namespace (`<team>/` prefix law) and an advisory index; a content-hash key would dedupe two DIFFERENT graphs that happen to share a fingerprint or split one lane across edits, and the incumbent-wins law only makes sense when the caller owns the key's meaning. `submit`'s optional `lane` field rides the same law: a label for triage, never scheduling.
- **`wait` `timeout` — default 600 s, hard ceiling 1800 s; self-yields at ~330 s.** A first-time user wishes `wait` blocked until terminal. Current is right: the host harness kills any tool call at its own deadline, so an honest ceiling + `timeout_note` on the clamp + a "call wait again" yield beats a silently-killed call. Long runs are the runner's job, not the tool call's.
- **Node `timeout` — default 900 s (meta `node_timeout` overrides); `shape` fills from measured p95 presets (recon 2400 s / build 1500 / review 2400 / publish 1500, `DEFAULT_SHAPE:"build"`); ceilings 86400 s and `max_turns` 200.** A first-time user wishes the bare 900 s default were shape-aware without opting into `shape`. Current is right: the presets are measured census numbers and applying them silently would make budgets invisible in the graph; the author who omits `shape` asked for the plain floor. The ceilings are there to refuse, loudly, not to negotiate.
- **`model` — default: unset = the profile's default model; `require_route` default TRUE only on nodes that pin an explicit model.** A first-time user wishes the tool picked per-node models by difficulty. Current is right twice over: inventing a model choice the author didn't make bills a route nobody authorized (an absent field reads `unknown`, never invented), and the fail-closed pin means a dead pinned route refuses the launch instead of quietly billing the ladder. An unset model riding the profile's default is the only honest default on a profile whose owner owns the routing table.
- **`run` `name` — default `workflow` (graph's `name` key, else the literal).** A first-time user wishes the run dir were named after its first agent's goal. Current is right: names are user-visible strings; goal text is arbitrary prose (paths, secrets, newlines) and run ids double as directory names — the strict-identity law (no silent normalization) outranks prettier dirs.
- **`save` `description`/`tags` — default: absent = the pre-#50 bare bytes.** A first-time user wishes saves were always enriched. Current is right: the solo golden freezes the default bytes (byte-identical law), and the normalizer makes either shape list and replay, so enrichment is opt-in. A missing recipe names the defect and optional alternatives, never requires curation.
- **`submit` `why_not_library` — default: REQUIRED (>=80 chars), no default.** This applies only to an explicit study submission, not execution. Existing submission validation and persisted receipts are unchanged.
- **`submit` dedupe — default: on, by graph digest + submitted_by, and it is a HINT (`{deduped, existing}`), not a bounce.** A first-time user wishes a resubmit silently overwrote the first copy. Current is right: the inbox is evidence for a human loop, so the tool never mutates or replaces stored receipts; a restatement reports the existing id and the human dedupes with the digest in hand.
- **`library` unknown shapes — default: skipped + LISTED in `skipped`, never a crash.** A first-time user wishes a corrupt file were auto-repaired or hidden. Current is right: repairing another profile's file is not the library reader's authority (same-UID trust boundary), and hiding it would make a broken entry un-findable; the listed warning is the repairable truth.

## Wedged runner.lock and the `release_lock` escape hatch (#44)

The field shape (2026-09-29): the runner and its children are gone, yet a fresh
`LOCK_EX|LOCK_NB` on `<run>/runner.lock` returns Errno 11 forever while a new file in
the same dir locks fine — the holder is a kernel-side orphan / inherited-fd survivor
beyond our `/proc` view. Left alone, `wait`-resume is permanently impossible.

Three laws keep recovery safe (`wfcommon.py`, pinned by `tests/test_lock_wedge_44b.py`):
- **Child-probe**: every read-path flock probe runs in a short-lived child whose death
  IS the release; the door never opens `runner.lock`, so a SIGKILLed door cannot strand
  an fd it never opened. The probe never creates the lock file.
- **Tri-state read**: the lock truth of a run dir is `free | busy | eacces | wedged`,
  never a bool. EACCES on an existing lock is its OWN fail-closed state (never free —
  a permission failure proves nothing about holders); `busy` is resolved against the
  kernel ledger (`/proc/locks`, seam `WF_PROC_LOCKS_PATH`) and the admission lease
  (`runner.lease {pid,boottime,at}`, heartbeated by the live holder). `wedged` requires
  probe EAGAIN AND zero ledger rows for the inode AND a proven-dead lease.
- **Safe heal**: `release_lock` (door verb) / `wf.py release-lock <run_id>` renames the
  stranded inode aside (never unlinks — evidence kept) and hands the lane a fresh lock
  path, ONLY under the admission heal-barrier (`runner.lock.heal`), and re-verifies
  probe + ledger + lease immediately before the rename: a holder that wakes between
  check and commit shows its row and the heal refuses — the holder wins. Read verbs
  (`status`/`list`) never heal; `wait` heals only the automatic `wedged` shape; a
  legacy lease-absent dir refuses automatic healing and needs the explicit operator
  verb. A heal never steals from a live holder and never heals on EACCES.

## Library provenance

`save` stamps provenance on EVERY entry: `{owner, version, source, saved_at, source_digest}` — `owner` defaults to the launcher profile (`save owner:<name>` ≤64 overrides), `version` is the plugin release that wrote the entry and is always present, `source` is the optional (≤512 chars) origin note. This DEFAULT-ON law (#126, owner ruling 2026-10-15) retires the 1.1 RATIFY F5 opt-in: pre-existing entries — bare or carrying the old four-key stamp — keep loading and listing verbatim (golden-solo bytes unchanged; no migration). `library` rows surface `owner`/`source`/`source_digest` when present; `run from:<name>` copies the stamp into run.json as `graph_source`. Provenance is attribution, never permission: no veto, no ACL.

### The `run_context` binding contract

A graph may declare, as its top-level `run_context` key, the launch bindings it needs: `{"required": ["target"], "defaults": {"target": "main"}}` — `required` an optional list of {run.KEY} identifiers (each must be referenced in the graph's operative text), `defaults` an optional map of non-empty strings applied where the launch is silent (a launch binding overrides them). Shape is validated at save/submit under the run_context key grammar. Enforced at run launch BEFORE any run write: missing required keys reject with `error_type:"missing_run_context_keys"` and `missing_run_context_keys:[...]`; a seed (string) binding cannot satisfy a contract (`run_context_contract_seed`). Bound values reach prompts — never bind secrets.

## Global agent-seat admission (pool-level)

Admission arbitrates against the POOL, not the inheriting process: the first
admission into a seats dir records its resolved cap in `<seats>/.cap` (first
writer wins, serialized by the pool's `.lock` flock — the recording and the
count-then-admit are one cross-process atomic step) and every admission after
it — nested child runners included, whose inherited env may carry a stale,
missing or default `WORKFLOW_MAX_SEATS` — counts tickets against that RECORDED
value, never its own environment. Env/.env files (read fresh, est-gxjh6) seed
the first acquirer only. A run.json `max_seats` acts as a per-run CEILING under
the pool cap: the run may hold fewer seats than the pool allows, never more.
`WORKFLOW_MAX_SEATS=0` stays a LOCAL disable of the semaphore and never touches
pool state. Operators change a live pool's cap by removing `<seats>/.cap` while
the pool is idle (the next first acquirer re-seeds it). A corrupt `.cap` is
re-seeded, never trusted, never fatal; an unwritable pool degrades to each
caller arbitrating its own seed.

## RunBudget: tokens-only run caps (est-3acn)

`budget: {"tokens": N}` caps provider-metered tokens — at the graph root (whole run;
door-baked into run.json `meta.budget` at submit, does not ride amends) and/or per node.
USD is deliberately NOT a key: an author who writes `budget.usd` is REFUSED at admission,
never ignored (the repo cost-trust law, issue #124 — estimated dollars are not a cap
surface). Enforcement is PRE-DISPATCH at the run_child seam beside the route-substitution
hold: spend comes from the same `child_metrics` join the read model shows (in+out+
cache_read+reasoning, summed per lane across attempts), NEVER estimated post-hoc. The law
is `spent + est_next >= cap` refuses, where est_next is the measured per-attempt mean
(node lanes first, run mean as fallback, floor 0 with no history — a cap never blocks the
first attempt). A refusal emits `dispatch.refused {node, index?, scope, cap, spent,
needed, error_class: budget_exhausted}` and bills ZERO attempts (the seat is never
touched); the class is terminal — outside every retry/fallback whitelist. A capped fan-out
commits `partial` WITH its surviving harvest (or `failed` on zero harvest, same class).
At the wave boundary the runner writes `budget_ledger.json` (`exhausted_nodes`,
`never_launched`), finalizes `run.partial`, and exits verdict `budget_exhausted`;
`run_state`/`status` then read `status: partial` with the derived `budget` view
(`cap_tokens`, `spent_tokens`, `per_node`, ledger fields) — terminal, `next: []`.
Raising a cap is an amend: `budget` is policy, excluded from the node efp (same law as
`run_budget`), so committed nodes stay frozen and replay-skip holds.
